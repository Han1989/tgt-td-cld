## Commands

Run everything from the repo root. You need Node ≥ 22.12 and npm workspaces.

| Command | What it does |
|---|---|
| `npm install` | Install all workspaces |
| `npm run dev` | Start the Vite dev server for the client (http://localhost:5173); local solo mode unless `VITE_SERVER_URL` is set |
| `npm run dev:server` | Run the game server with reload (ws://localhost:8080; allows localhost:5173/4173) |
| `VITE_SERVER_URL=ws://localhost:8080 npm run dev` | Client in online mode (lobby) against the local server |
| `npm test` | Vitest across all workspaces: unit tests, headless balance runs, the 3-bot server integration test |
| `npm run test:e2e` | Playwright browser tests (`apps/client/e2e`): builds `apps/client/dist-e2e` with `--mode e2e`, then runs portrait iPhone / Pixel emulation, desktop and PWA tests in Chromium, and last, alone (the `perf` project waits for the others), the 300-creep stress test (1.5–3 min: a fixed number of frames, so slower machines take longer); `?lab&auras` starts heroes with E learned, `?lab&ult` with R. CI runs each project (sharded) in its own job and the stress test alone in `e2e (perf)` (`--project=perf --no-deps`); `ci` aggregates them. On CI each browser test (not the stress test) gets one retry, and a test that passes only on its retry is listed as flaky in the job summary and as a warning annotation (`.github/scripts/playwright-summary.mjs`). **Off CI it refuses to start unless spec files are named (`e2e/localRun.ts`): in a session run single specs, never the whole suite (Session rules).** |

## Session rules

For every agent session (Claude Code, Cursor or any other). They keep a session short.

- **Before each push:** `npm test` and `npm run build`, run after your last edit, docs and tracker included (`apps/client/test/progress.test.ts` checks the tracker's counts).
- **Browser tests in a session: only the specs you changed or that cover what you touched, once.** Build with `npm run build:e2e -w @tdt/client`, then from `apps/client` run `npx playwright test e2e/<name>.spec.ts --project=<project>` (`iphone`, `pixel` or `desktop`; `playwright.config.ts` lists the specs each project runs). The stress test on its own: `npx playwright test --project=perf --no-deps` (without `--no-deps` it runs every other test first).
- **Never the whole browser suite in a session.** It takes over half an hour there. CI runs it in about 11 minutes, split over seven jobs, on every pull request, and `ci` is the required check. Off CI the runner refuses a run that names no spec file (`apps/client/e2e/localRun.ts`): don't set `TDT_E2E_ALL` to get past it. Where a task or an older doc says "`npm run test:e2e` passes", it means on CI.
- **A spec that fails:** run that one spec once more on its own. If it passes, say so in the pull request and move on. A test that fails only on a busy machine is for CI to judge.
- **Don't wait for CI:** no polling, no monitors, no timers or check-ins.
- **When the pull request is open, stop.** Turn on auto-merge first if the task says so, unsubscribe the session from the pull request's activity if it was subscribed, write the summary and end. If CI fails, a new session takes it.
- **A merged or closed pull request ends the task.** A session that is resumed checks the pull request's state before it does anything else.

## Architecture rules

- **The sim is pure and deterministic.** `packages/sim` has no DOM, no Node APIs and no networking. Its tsconfig uses `lib: ES2022` and `types: []`, so using them fails to compile. It uses a fixed 20 Hz timestep (`TICK_RATE`) and the seeded RNG in `rng.ts` (state is kept in `GameState.rng`). **Never** use `Math.random()`, `Date.now()` or `performance.now()` in `packages/sim`; a test enforces this.
- **The sim API** is `createGame(config, seed)`, `applyCommand(state, playerId, command)`, `step(state)` and `snapshot(state)`. The state is a plain, mutable, JSON-able object. `snapshot()` never mutates it. Hosts also call `setPlayerConnected` (drop / rejoin) and `setPlayerLeft` (gone for good: their empty pads open to everyone).
- **Match modes are tuning.** `createGame(config, seed)` takes `config.mode` (`full` default, `quick` or `endless`) and stores `tuningForMode(tuning, mode)` in `state.tuning`: the engine only ever reads `state.tuning`, never the mode. Mode numbers live in `TUNING.modes.<mode>` (partial `economy` / `waves` / `playerScaling` / `hero.xpForLevel`, Hard bands, the boss shield, `endless` to turn on the loop in `tuning.endless`, and `hero.veteran` / `reinforce` to turn on Endless's veteran levels and Reinforce); a mode may set its own `difficulty`, which `createGame` uses whatever the config asks (Endless is Hard). Waves past the list exist only in Endless: read any wave's creeps with `waveGroups(tuning, wave)` and the match's last wave with `lastWave(tuning)` / `totalWaves(state)` (`maxWave` in Endless), never `waves.list[wave - 1]` or `snap.totalWaves` as the list's length (bots time their thirds by `tuning.waves.list.length`). Code outside the sim that needs a mode's numbers (bots, HUD) calls `tuningForMode(TUNING, snap.mode)`.
- **Maps are data.** A map is a `MapData` object (`src/maps/*.ts`): size, lanes (waypoints, portal first, Heart last), Heart, hero spawn, pads with zone tags (`west` / `mid` / `east`, `extra` for 3-player teams), pad size and the safe-zone row. `buildMap` derives the tile grid; `getMap()` returns Spire. Never hard-code map coordinates in engine code or bots: derive them from the map (lanes, `heroSpawn`, pads).
- **Team size:** a match holds **1–3 players, one per lane** (`MAX_PLAYERS` in the protocol): rooms answer a 4th join with `room_full` and `createGame` throws on more. Per-team-size tuning tables (`playerScaling`, `pads`) have 3 entries.
- **Pad zones:** `padLayout` decides which pads exist for a team (base pads, plus `tuning.pads` extra pads per lane zone by player count) and who owns them (solo: all; 2 players: West + west half of Mid / East + east half; 3: West / Mid / East). `state.pads` / `snapshot.pads` hold `{ id, owner }` (owner `null` = open to all). `build` is rejected on pads that aren't in the match or belong to a teammate.
- **Hosts run matches through `Match`** (`match.ts`): `createMatch(config, seed, build)` (the host's git commit or `dev`, stamped into the report and replay: the server's `RENDER_GIT_COMMIT` via `ServerConfig.build`, solo the client's `VERCEL_GIT_COMMIT_SHA` via Vite's `__BUILD__`), `matchCommand` (rounds command coordinates to 1/100 tile, logs `[tick, player index, type, …args]`), `matchPresence` (`join` / `drop` / `leave`, logged too) and `matchStep` (also counts the report's numbers). Everything the host applies goes through them, in the order it applies it, so `replayMatch(matchReplay(m))` re-runs to the same state (the server integration test checks it). When the match ends the host sends `{ t: 'report', report, replay }` once (the server again to a player who rejoins after the end) and the server logs `reportSummary`. Headless balance runs and bots still call `applyCommand` / `step` directly.
- **Events:** sim code emits into `state.pendingEvents`. At the end of `step()` they move to `state.events`, which the next `snapshot()` carries. Hosts apply commands, then `step`, then `snapshot`.
- **The client never mutates game state.** It sends `Command`s through a `Transport` and renders `Snapshot`s. Your own hero is the one exception to *where* things are drawn: while the joystick or a move order steers it, `HeroPredictor` (`predict.ts`) draws it walking at once along the sim's path and blends it back to the snapshots (jumping only past 1.5 tiles); the server stays authoritative. Everything else is drawn from the interpolation buffer. Client-only UI state (input mode, selection, markers) lives in `uiState.ts`.
- **Transport:** `LocalTransport` runs `SimHost` in a Web Worker; `NetworkTransport` talks to the game server. Both exchange *encoded* protocol messages and both deliver complete `{ t: 'snapshot' }` messages to the game view. `NetworkTransport` rebuilds them from keyframes + deltas, so the renderer and HUD never see deltas.
- **The server is authoritative.** Each room owns the only real `GameState`. Commands are queued as they arrive and applied at the start of the next tick, in arrival order; then `step`, `snapshot`, and a broadcast (a full snapshot for new or reconnected clients and every `keyframeEveryTicks`, otherwise one encoded delta shared by all clients). Never trust anything from the client beyond a decoded message.
- **Rooms are self-contained** (lobby, sim, sockets in one process). Room codes start with the server's `SHARD` letter so a future router can route by code (docs/DEPLOY.md §7). Keep Render at one instance per shard.
- **Server config comes from env** (`config.ts`). Tests build configs with `defaultConfig({...})`, e.g. `tickMs: 1` to run game time fast.
- **Damage:** every hit goes through `damageMultiplier` (`combat.ts`): physical is reduced by armour, magic by magic resist, for creeps, heroes and towers alike. Creeps carry their current `armor` / `magicResist` (bosses change theirs). Bosses are creep kinds with `boss: true`; test for the flag, never for a kind name.
- **All balance numbers live in `packages/sim/src/tuning.ts`.** Durations are in seconds, distances in tiles and speeds in tiles/s. Convert with `secondsToTicks`. Don't scatter constants. Hero skills live under `tuning.hero.<kind>.<skill>`, with per-rank arrays (4 entries for Q/W/E, 3 for R). Q and W cost mana; ultimates (R) have no `manaCost` (cooldown only). Mana regen is `manaRegen + manaRegenPerLevel × (level − 1)` plus Clarity Aura.
- **Hero skills:** `skills.ts` owns every Q/W/E/R (`SKILL_MODES` says instant / point / passive). A new skill needs its tuning, a case in `skillInfo`'s tables and `castInstant` / `castAtPoint`, display text in `apps/client/src/heroInfo.ts`, and a test in `packages/sim/test/heroes.test.ts`.
- **Units:** the sim works in tiles (floats). The renderer multiplies by `TILE_PX` (32). Pads are `map.padSize` tiles square (3 on Spire).
- **Layout and touch (docs/MOBILE.md §4–5):** `computeLayout` decides everything about the screen (tall / wide / rotate, tile size, control positions, follow range, the ⤢ button) from the viewport, safe-area insets, touch and orientation; `GameView` applies it. **Phones: the camera is no longer locked at the fit** (V-07e): a pinch zooms it in up to 1.8× and it follows your hero (`PhoneZoom` in `input/camera.ts`, fed by `TouchControls`; the wheel and drag-pan stay desktop-only, `camera.locked`); every screen ↔ world conversion goes through the camera, so taps, pings, rings and aim work at any zoom; the controls still never cover gameplay (followed as far as it goes, every gameplay row is above them). Top bar is 44 px (the map must fit 412 × 839). Keep layout and gesture rules as pure functions in `layout.ts` / `touch/gestures.ts` with unit tests; `touchControls.ts` only wires them to DOM and pointer events. Canvas input splits by pointer type: mouse → `Controls`, touch / pen → `TouchControls`. Radial menus in the tall layout and on touch screens, desktop panels otherwise. The controls must never cover gameplay (lanes, pads, Heart) and radial menus must never cover the controls; the layout and e2e tests check both.
- **Analytics respect the Play data switch.** Every post goes through `createAnalyticsClient`'s `send`, which reads `analyticsOn()` (`analytics/preference.ts`) first, or, for the anonymous counts with no id (`/analytics/count`, D-10), `createCounter`'s `count`, which reads `countOn()` first; never post analytics around them. A new event or count field needs a line on `privacy.html` (a test lists the fields). The two boards' posts (a Daily run's Post my run, an Endless run after the player's yes) are the player's own act and do not read the switch; they follow the age rules instead (never under 13; Endless 13–15 one tap each run) and say so on `privacy.html` (a test lists its sentences).
- **PWA:** the service worker is generated by `vite.config.ts` and only serves same-origin GETs (never the WebSocket). It precaches the shell, the map plate and the structures' sheet with it; the creeps' and heroes' match sheets are not precached (`isOnDemandSheet`): each is kept in the version's cache the first time the page asks for it (V-07d), so an install never shares a first visit's line with the sheets its first match waits for. A page load gets the game (`index.html`) unless the path is another page of the shell (`privacy.html`). Solo pause is a worker control message (`{ ctl: 'pause' }`), not a protocol message. `import.meta.env.MODE === 'e2e'` code (the `window.__tdt` hook, `?lab` gold, `?analytics` posting solo play data to the page's own origin for `e2e/privacy.spec.ts`) must stay out of normal builds.
- **Art (docs/ART.md).** Art is **made by scripts in the repo**. Heroes, creeps and towers are 3D models, never modelled in code: **the heroes are the game's own designs generated in Meshy** (`tools/blender/assets/meshy/`, Han's decision of 22 Oct 2026, V-06b; their own skeleton and clips, `rig='meshy'`), and so are **all nine creeps and bosses** (`tools/blender/assets/meshy/creeps/`, V-06i and V-06j: the Spire's host, `docs/art/enemy-style.md`), **the five towers too, their ten branch turrets, the Heart and the portals, theme A, the Spire's wards** (`tools/blender/assets/meshy/wards/`, V-06l batches 1 and 2, Han's pick of 24 Oct 2026: a body and a turret a kind, a turret a branch, the Heart and a portal one model each); **the CC0 KayKit packs** (`tools/blender/assets/kaykit/`; Han's decisions of 16 and 17 Oct 2026) remain only for the kit's small additions on the wards (the tiers' runes, braziers, candles and columns, a branch's outline, the Heart's rubble and flames), the HUD's frames and the Ranger's arrow (the map plate's props are the clearing's own, made in code), and the Quaternius monsters the Wisp and the bosses were stay in `tools/blender/assets/quaternius/` for the `LEGACY` rows; all of them imported, posed by their own clips (by bone name, retimed to the 2D rigs) and repainted in Runelight's tokens by the painter in the repo (`tools/blender/tdt3d/npr.py`; a Meshy texture's colours are matched to the colours the row expects, each mapped to a token, and an unexpected colour stops the build, as an unmapped KayKit palette cell does); one table, `tools/blender/hero.py`, holds the three heroes (model, the weapons Meshy welded into the mesh rebound whole to a hand, texture colours to materials, layers, props on the hands, clips, stage loop, match frames), and `npm run art:3d -- <hero>|heroes` **renders them ahead of time** into pictures and videos (docs/ART.md §15): the match sheet and its layout in `src/render/art3d/` (played by `Hero3DRig` on `HeroRigBase` once loaded, after the first screen, keeping each 2D rig's timing; the 2D rigs are the fallback and stay in `?showcase`), the lobby stage's loop, poster and empty clearing in `public/stage/` (`lobby/stageBackdrop.ts`; one clearing and one box for all three, so the stage swaps heroes without moving; the videos cached on first play, never precached). The creeps likewise from one table, `tools/blender/creeps.py` (`rig='meshy'` rows imported as a hero is, their welded weapons and every mis-skinned part rebound whole to one bone, thin limbs thickened; a model with no skeleton (the Wisp, the Hatchling, the Ironhorn, the Shardback) posed from its bind pose, `posed` and `tdt3d/posed.py`; the pack rows they replaced kept as `LEGACY`): a match sheet per kind (no stage), played by `Creep3DRig` (`CreepRigView` shared with the 2D `CreepRig`) once loaded; the nine sheets must fit two 2048 × 2048 pages (a test checks). The towers, the branch turrets, the Heart and the portals (Meshy `ward` pieces, painted from their texture, a welded moving part posed from its vertices; the Heart's damage stages painted, posed and cut from its one model; and the kit's additions) are in one table, `tools/blender/structures.py`, rendered into one sheet on one page (towers seen straight down so the turret turns truly; the Heart and portals from the south), played by `Tower3DRig` (on `TowerRigBase` with the 2D `TowerRig`) and `Heart3DView` / `Portal3DView`. The art loads after the first screen in Han's order: the map plate, the structures' sheet, the creeps', the heroes' (`artLoad/order.ts`); the picked hero's sheet starts the moment the home card shows him, and when a match starts everything its first wave shows starts at once, a solo match holding its start for it at most 6 s (V-07d, `artLoad/`). **The match view's frames** are rendered the same way (V-07a): `tools/blender/ui.py` into one sheet (`src/render/art3d/ui.webp`, loaded right after the plate), cut by `hud/frames.ts` into CSS 9-slices and faces that `style.css` uses only under `<html data-ui="ready">` (paint only: no border width, padding or size changes; the CSS look is the fallback, and the lobby keeps it). **Nothing 3D runs on the device**: no three.js, no glTF, no second WebGL context, no model file in the client (`test/art3d.test.ts` checks). The outputs are committed; CI does not run Blender, and a unit test checks the layout data against the images and the fringe check on every hero's fixtures. **The map has its own palette rows** (V-07c): `grass`, `road`, `padSand`, `mapCanopy`… in `tokens.ts`, read by the map build (`tdt3d/map.py`, which paints the clearing library it borrows with them, `MAP_TOKENS`), the painted ground, its props and the pad slab; the figures, the lobby's clearing and the HUD keep the ground tokens (`moss`, `lane`, `padStone`…), so the map's look changes without rendering anything else again. **The map's ground is a rendered plate** (V-03, docs/ART.md §16): `npm run art:3d -- map` builds a Blender scene from the map's data (`tools/blender/mapdata.ts`: `getMap()`, `padLayout`, `propSpots`; never typed coordinates) and renders it straight down into one WebP (`public/map/spire.webp`, 1664 × 3200, under 700 KB, precached with the shell; pads only bigger teams have are patches in `spire-extra.webp`), its layout (files, the pad squares and lane lines measured in the render, the prop spots) in `src/render/plate/spire.json`, checked by `test/plate.test.ts`; `WorldRenderer` draws it as one sprite under everything, Bright as one `screen` wash sprite over it, the pads' zone tints over it as before; **`ground.ts` (the painted ground) is the fallback** until the plate has decoded. Muted means no audio work at all. **Recorded files** replace code-made sound with no code change: `public/music/{lobby,match,boss}.mp3`, `public/sfx/<sound id>.mp3` (docs/SOUND_FILES.md); the build lists them, the game trims their silence and levels them, and the service worker caches them on first play, never on install. **A music file starts streamed** (P2-11, docs/ART.md §13): an `<audio>` element per file on the music bus (a `MediaElementAudioSourceNode`), the scene's played inside the first tap (`onUnlock`: `play()` there, then connect, as iOS needs; the others played and paused there with no source) and the match's as a match is created (`GameAudio.matchStarting`), fading in over 1.5 s at the level measured at build time (`src/audio/musicLevels.json`, `npm run music-levels -w @tdt/client`; else the last decode's, else 0.7); it is decoded once the element holds the whole file (the browser's cache answers: one download) and the decoded loop takes over at the element's loop point or in a 0.5 s crossfade; the recorded effects load once the music has sounded. Without a stream nothing plays while the file downloads (P2-10); the code-made score (fading in over 1.5 s) plays a scene only when the build has no file for it or the stream and the decode both fail. No cue note. A new effect needs a row in `public/sfx/README.md`.
- **Effects are client-only** (never in the sim): `WorldRenderer` derives them from snapshots (HP drops = hit flashes, new projectiles = shots) and events, and plays them through `Effects` (`render/fx/`). The sim only reports facts: damage numbers come from its per-tick `damage` events (who dealt how much to which creep), all of them solo and only yours online (`HitTracker.feed`). Everything is pooled: particles go in the four `ParticleContainer` layers via `fx.emit` / the recipes; persistent visuals (zones, Heart, portals, auras, trails) are created once and animated by transform / alpha / tint only. Mark an effect `essential` only if it shows gameplay (areas, hits); the rest disappears at Graphics → Low (`fxLevel`). Shake goes through `fx.bump`, which honours Low and the Screen shake setting. A hit-stop or a slow-down goes through the one `RenderClock` (`GameView`; `HitStop` in `render/fx/juice.ts` decides which events hold it; at most 150 ms held in any second, none under reduced motion), never a timer of its own; the camera's zoom-punch (`WorldRenderer.punch`) goes with the shake. `FxLevel.calm` (the device's `prefers-reduced-motion`, re-read when the OS setting changes) is for the effects that move: the Rampart Slam guard ring, the rain strikes and the Meteor Rain fuse burst keep their rings and flashes and drop streaks, sky, bloom, turning, blinking, embers and shake (the fuse band is DOM, `CoopStage.fuse`: its CSS fades under `prefers-reduced-motion` instead of unrolling); other effects do not read it yet.
- **The client may import static data from `@tdt/sim`:** `getMap()`, `TUNING`, `tuningForMode`, `towerTier`, `towerStats`, `repairCost` (the price the Repair button shows), `TILE_PX`, `TICK_RATE`, `padAtTile`, the pure wave lists `waveGroups` / `endlessWave` / `lastWave` (Endless's waves past the list: boss banners, music, the Wisps lesson), the Daily run's pure day helpers `dailyKey` / `shiftDailyKey`, Endless's `reinforceCost` / `reinforceMultiplier` (the price and the stats Reinforce shows) and `heroLevelXp`, and the pure map pathfinding `findPath` / `nearestWalkable` (own-hero prediction walks the path the sim will). Pad ownership comes from `snapshot.pads`. It must not call sim functions that touch game state (`LocalTransport` / `SimHost` are the exception, since they *are* the host, and so is the `?stress` scene's `StressTransport`).
- **Protocol validation:** `decodeClientMessage` rejects unknown types, extra keys, non-finite or out-of-range numbers, and oversized messages. Game-rule validation (gold, range, cooldowns, ownership) happens in `applyCommand`, which emits a `rejected` event instead of throwing.

## Conventions

- Strict TypeScript everywhere (`strict`, `noUncheckedIndexedAccess`, `noUnusedLocals`, `verbatimModuleSyntax`). Use `import type` for types.
- Workspaces export TypeScript source directly (`"main": "src/index.ts"`). There is no per-package build step; Vite and Vitest compile from source.
- ES modules, 2-space indent, single quotes, semicolons, trailing commas, ~120-column lines.
- Every sim mechanic gets a Vitest unit test. Use the helpers in `packages/sim/test/helpers.ts` (`labGame`, `placeCreep`, `parkHero`, `run`, `tuningCopy`) for isolated mechanic tests.
- **Balance targets (Spire, playtest 2; `docs/GAME_DESIGN.md` §13, `docs/balance/`):** Normal is for first-time players, Hard for players who know the game. Novice bots win at least 80% of the seeds for every team on its own (each solo hero, each pair, the three), in both modes; casual bots win with 50–90 Heart (`HEART_TARGET`); expert bots finish Normal with 85 or more (`EXPERT_NORMAL_MIN`) and Hard with 40–80 (`HARD_TARGET`); casual Hard may lose. Teams (2 and 3 players) keep the curve (last third ≥ 25% of the Heart lost, first ≤ 45%). - Towers: per-tier numbers live in `TUNING.towers[kind].tiers` (tier 1 = build); read them with `towerTier(tuning, kind, tier)`. After the last tier a tower upgrades into one of its two branches (`TOWER_BRANCHES` in the protocol, numbers in `TUNING.branches`): tier 4, `tower.branch` set, final. The `upgrade` command carries `branch` exactly then (the sim rejects it before, and rejects a plain upgrade at tier 3). Engine code reads a tower's numbers with `towerStats(tuning, kind, tier, branch)`, which merges the branch's effects (`TowerEffects`) over plain defaults (`NO_EFFECTS`); plain-tier shots carry no `fx`, so they behave exactly as before branches. A new branch effect needs a `TowerEffects` field, handling in `towers.ts`, a stat row in the client's `towerInfo.ts` and a test in `branches.test.ts`. **Repair** (`repair` command, owner only) restores full HP at once for `repairCost(tuning, tower)`: whole HP as snapshots show it (`Math.ceil`), so the client's price is the sim's; it never touches `spent` (the sell refund and the next repair's price stay on the tower's own price). **Reinforce** (`reinforce` command, owner only, Endless only: `tuning.reinforce.on` from `modes.endless`, a branched tower) buys rank after rank for `reinforceCost(tuning, tower)` (the kind's tier-3 price × `priceGrowth`^rank, whole gold, shared with the client as `repairCost` is); `towerStats(…, rank)` multiplies damage and max HP by (1 + `perRank`)^rank and nothing else, the price joins `spent`, and the rank is `tower.reinforced` (in the snapshot); Full and Quick refuse it, so their towers are as before. An upgrade keeps the damage taken: it adds the new tier's extra max HP to the current HP.
